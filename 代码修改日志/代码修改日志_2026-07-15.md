## 二、问题项与修改动作

### FIX-01：时间轴缺少播放、暂停和倍速功能

**问题现象**

- 页面只有“下一步”和“重播”。
- 规格要求的播放、暂停、1x、4x、16x 不可用。
- `useClockDriver` 已存在，但未在应用中挂载。
- 拥堵增长和预测兑现只能通过手动跳步展示。

**根因**

- `App` 未调用模拟时钟驱动。
- `Timeline` 未订阅 `running`、`speed`、`toggle` 和 `setSpeed`。

**修改动作**

- 在 `App.tsx` 顶层调用 `useClockDriver()`。
- 在时间轴增加“播放/暂停”按钮。
- 增加 1x、4x、16x 倍速按钮及选中态。
- 播放期间禁用调试步进，避免时钟和手动步骤并发推进。
- 保留“下一步”作为彩排与调试入口。

**涉及文件**

- `src/App.tsx`
- `src/components/Timeline.tsx`
- `src/engine/clock.ts`（复用既有驱动）

**验证结果**

- S1 在 16x 下可自动推进至 15:20:18，并在交互点自动暂停。
- 播放、暂停和三档倍速均可操作。

### FIX-02：暂停点可绕过待办确认

**问题现象**

- 控制类措施未确认时仍可点击“下一步”。
- S5 可在 V1 有 5 项待确认时直接生成 V2。
- 后续版本可能把未确认措施直接标成“已下发”。

**根因**

- `stepNext` 未处理场景动作的 `pause` 属性。
- 门禁没有独立状态，无法区分普通中间步骤和明确标注的交互暂停点。

**修改动作**

- 增加 `waitingForConfirmation` 状态。
- 自动播放执行到 `pause=true` 动作后：停止时钟并进入确认等待态。
- 手动步进执行到暂停动作后同样进入确认等待态。
- 仅在暂停点存在未确认措施或强制打断时阻断继续操作。
- 完成全部待办后，播放和“下一步”自动解锁。
- 未标注暂停的中间推理步骤即使已经生成草案，也可继续推进，避免 S1/S2 被提前卡住。

**涉及文件**

- `src/store.ts`
- `src/components/Timeline.tsx`

**验证结果**

- S0 到达 V1 初报后，“下一步”显示“请先确认待办”并禁用。
- 完成两项控制类确认后按钮恢复。
- S2 中间步骤存在待办时仍可继续，最终暂停点才执行门禁。

### FIX-03：后续确认会篡改历史版本

**问题现象**

- 在 V2 中确认继承措施后，切回 V1，V1 同名措施也被修改为“已下发”。
- 历史版本待办数量随最新版本操作变化。

**根因**

- `confirmMeasure` 只按 `planId + measureId` 匹配。
- 同一事件多个版本共用 `planId`。
- 继承措施沿用旧措施 ID。

**修改动作**

- 确认接口改为 `planId + version + measureId`。
- 只更新精确命中的版本和措施。
- 继承措施生成新的版本级实例 ID。
- 历史版本措施对象不再被后续版本操作修改。
- 为测试环境增加安全的 `window` 存在性判断。

**涉及文件**

- `src/store.ts`
- `src/components/TodoQueue.tsx`
- `src/scenarios/types.ts`
- `src/scenarios/util.ts`

**验证结果**

- V2 确认完成后切回 V1，V1 措施状态保持原值。
- 自动化测试“只在暂停点阻断，并保持历史版本只读”通过。

### FIX-04：浏览历史版本会重新激活旧待办

**问题现象**

- PlanPanel 切换到 V1 后，TodoQueue 也同步切到 V1。
- 已被替换版本的待办可以重新操作。

**根因**

- PlanPanel 和 TodoQueue 共用 `activePlanVersion`。
- 版本浏览状态与执行队列状态未分离。

**修改动作**

- PlanPanel 继续使用 `activePlanVersion` 进行历史浏览。
- TodoQueue 改为始终选择最新的、未完成且未被替换的可执行版本。
- 浏览历史版本不再影响实际待办队列。

**涉及文件**

- `src/components/TodoQueue.tsx`

**验证结果**

- 切换至 V1 时，待办队列仍绑定 V2。
- V2 全部确认后，浏览 V1 时确认按钮数量为 0。

### FIX-05：S4、S5 新版本未替换旧版本

**问题现象**

- S4/S5 通过 `upsertPlan` 写入 V2 后，V1 仍显示“已下发”。
- 不符合新版本生成后旧版本转“已被替换”的状态机规则。

**根因**

- 只有 `reviseTo` 执行版本替换。
- `upsertPlan` 仅追加或覆盖，不执行状态流转。

**修改动作**

- `upsertPlan` 在插入更高版本时，统一调用 `supersedeState` 处理旧版本。
- 覆盖同版本时不重复触发替换。
- `reviseTo` 增加 `planId` 限定，避免误替换其他事件的同版本预案。

**涉及文件**

- `src/store.ts`
- `src/engine/stateMachine.ts`（复用既有 `supersedeState`）

**验证结果**

- S4 生成 V2 后，V1 显示“已被替换”。
- S5 生成重构版本后旧版正确归档为替换态。
- 自动化测试“场景直接写入新版本时也替换旧版本”通过。

### FIX-09：S2 资源 ETA 与计算结论矛盾

**问题现象**

- 计算面板结论为 W-01 等待释放后 41 分钟到位。
- 预案卡显示 ETA 48 分钟。
- `occupiedBy` 只用于地图展示，没有进入资源 ETA 计算。

**根因**

- 原 ETA 始终按资源驻点到目标点的直接车程计算。
- 未读取占用事件位置和作业阶段。

**修改动作**

- 根据 `resourceOccupancy` 查找资源占用方事件。
- 从占用事件 `stage` 中读取已作业分钟数。
- 按 `median 45min - 已作业时间` 计算剩余作业时延。
- 按占用事件位置到新事件位置计算转场时延。
- 新 ETA = 剩余作业时间 + 转场时间。

**涉及文件**

- `src/store.ts`
- `src/scenarios/s2.ts`（复用既有场景阶段和计算记录）

**验证结果**

- S2 预案卡和计算面板均显示 W-01 ETA 41 分钟。

### FIX-31：GIS 与数字孪生地图无法稳定渲染（初始化看门狗误判降级）

**问题现象**

- 部分环境下打开演示后，3D 数字孪生地图不出现，标题显示为“轻量 GIS”，状态提示“3D 地图画布初始化超时”。
- WebGL 明明可用（如 AMD Radeon 780M、`webgl2` 正常），MapLibre 仍被判定为初始化失败并永久降级到 Leaflet。
- 现象不稳定：同一台机器有时是 3D 数字孪生，有时是轻量 GIS，无法稳定复现，重复刷新结果不一致。

**根因**

- MapLibre 的 `load` 事件依赖 `requestAnimationFrame` 渲染出首帧后才触发。
- 原 6 秒看门狗从组件挂载即开始计时，且计时不区分页面是否可见。
- 页面在初始几秒处于隐藏/节流状态（后台标签、最小化、一键启动打开浏览器的瞬间、远程桌面未刷新、慢速机器首帧延迟）时，浏览器暂停 `rAF`，`load` 首帧永远不来。
- 看门狗因此在 WebGL 完全正常的情况下超时触发，把可用的 3D 地图误判为故障并永久切到 Leaflet。
- 经实测复现：`document.visibilityState = hidden` 时 `requestAnimationFrame` 不回调，`map.loaded()` 与 `isStyleLoaded()` 始终为 `false`，即使手动泵帧也无法完成初始化——初始化耗时本不该计入这段隐藏时间。

**修改动作**

- 将初始化看门狗改为“仅在页面可见时计时”：`document.visibilityState !== 'visible'` 时不启动计时，避免把正常的渲染节流误判为 WebGL 故障。
- 监听 `visibilitychange`：页面从隐藏恢复可见时，主动调用 `map.resize()` 与 `map.triggerRepaint()` 唤醒被暂停的初始化帧，然后才开始计时。
- 看门狗超时阈值由 6 秒放宽为 8 秒（仅统计可见时长），为慢速可见环境留出余量；真正的 WebGL 建画布失败仍由同步能力检测即时拦截，可见状态下长时间无首帧仍会按时回退。
- 组件卸载时清理看门狗定时器与 `visibilitychange` 监听，避免残留副作用。
- 同步增强 Leaflet 后备视图：其不自带 `ResizeObserver`，若在页面隐藏或容器 0 尺寸时初始化会保持空白；改为在 `ready` 后及页面恢复可见时主动 `invalidateSize()`，确保后台启动后仍能铺满并显示瓦片与路网。

**涉及文件**

- `src/components/LeafletTwinMap.tsx`
- `README.md`

**验证结果**

### FIX-33：3D 数字孪生地图黑屏——MapLibre 样式覆盖容器定位导致画布尺寸塌陷

**问题现象**

- 轻量 GIS（Leaflet）正常出图，3D 数字孪生（MapLibre）整块黑屏。
- 地图自身状态全部正常：`样式已载=true`、`地图已载=true`、`底图状态=在线`、图层无缺失、`queryRenderedFeatures` 有 39 个要素在渲染、WebGL 上下文健在、GPU 为真实硬件（AMD Radeon 780M / D3D11）。
- 现场诊断显示画布高度恒为 300px，宽度随不同次加载而异，**全屏后画布仍停在全屏前尺寸**（容器 1902×960、画布 867×474）。

**根因**

- 地图容器写为 Tailwind 的 `absolute inset-0`，但 `maplibre-gl.css` 的 `.maplibregl-map` 声明了 `position: relative`；二者同为单类选择器、优先级相同，而 MapLibre 样式在样式表中**后加载 → 覆盖生效**。
- `position` 变成 `relative` 后 `inset-0` 不再撑开元素，容器高度塌为 **0**（子元素均由 MapLibre 绝对定位，无内容高度）。实测容器 `867×0`，而其父层为 `867×474`。
- 容器高度为 0 → MapLibre 读不到有效尺寸，画布停留在初始化时的尺寸且再不跟随；画布只铺容器一角，其余露出父层底色 `#071727`，**表现为整图黑屏**。
- Leaflet 不受影响的原因：`leaflet.css` 不声明容器 `position`，其 `absolute inset-0` 始终有效——这正是「轻量 GIS 好、3D 黑屏」的分野。
- 附带根因：看门狗只校验 `load` 事件是否触发，不校验是否真的出图，故这类「加载成功但不出图」永远不会自动降级。

**修改动作**

- 地图容器定位改为**内联样式** `{ position: 'absolute', inset: 0 }`：内联样式优先级高于任何类选择器，且不受打包顺序影响，从根上免疫第三方 CSS 覆盖。
- 新增 `ResizeObserver` 显式监听容器尺寸，任何变化（全屏切换、窗口缩放、DevTools 停靠、面板布局变动）都即时 `map.resize()`；回调内**不得再套 `requestAnimationFrame`**——页面隐藏/节流时 rAF 不回调，画布将永不跟随。
- 修正字体栈：`glyphs` 指向的服务只提供 `Noto Sans Regular`，而未显式指定 `text-font` 时 MapLibre 用默认的 `Open Sans Regular,Arial Unicode MS Regular` → 每个标注 404。为全部 10 个 symbol 图层显式指定字体栈；中文标注改由 `localIdeographFontFamily` 本机渲染，不依赖外部字体服务。
- 新增「⚕ 诊断」按钮：地图不出图时就地显示画布/容器尺寸、WebGL、GPU、图层清单、相机与**正在渲染要素数**，并给出判读，避免让使用者翻控制台。
- 新增开发态 `window.__map` 句柄（与 `window.__store` 同一约定），便于现场诊断。
