## 0. 背景（为什么改）

运行模式多事件并发时实测（8 起活跃事件）：

| 面板 | 当前实际绑定 | 缺陷 |
|---|---|---|
| 统一待办（TodoQueue） | 只绑定**最新一起**事件的预案 | 全网 40 项待确认，35 项完全不可见（安全问题） |
| 预案与版本（PlanPanel） | 最新一起事件 | 与其他面板可能不是同一起 |
| 现场监控（MonitorPanel） | 写死默认 `CAM-1195` | 与当前处置事件无关 |
| 拥堵网格（CongestionGrid） | 按内部排序取前 6 行 | 规则对用户不可见，多行拥挤 |
| 推理轨迹（TracePanel） | 全部事件 40 步平铺混排 | 步骤卡不显示所属事件，无法区分 |
| 顶部事件 chips（RuntimeBar） | 横向滚动条 | 不能排序、不能扫视、不显示紧迫度 |

根因：**缺少「聚焦事件」主线**，各面板各自猜测显示对象。本清单以引入 `focusedEventId` 为核心，重组为「分诊 → 态势 → 决策 → 依据」四问结构。

## 2. 任务清单（按顺序执行，T1 完成前不得开始 T2+）

### T1【store】引入聚焦事件主线

**文件**：`src/store.ts`

1. `AppState` 接口新增字段与动作：
   ```ts
   /** 当前聚焦事件 id；运行模式下所有面板的统一显示对象。null=无聚焦。 */
   focusedEventId: string | null;
   /** 手动聚焦某事件；传 null 表示清除聚焦（随后由自动规则接管）。 */
   focusEvent: (eventId: string | null) => void;
   ```
2. 初始值：在 `freshScenarioState` 返回对象中加入 `focusedEventId: null`（`freshRuntimeState` 复用它，无需另加；`clearRuntime` 因走 `freshRuntimeState` 自动清空——验证这一点）。
3. **自动聚焦规则**（只在 `mode==='runtime'` 生效，全部实现于 store 内部，不放组件里）：
   - 规则 A：`ingestEvent` 结果为 `created` 且当前 `focusedEventId === null` 时，聚焦新事件；**已有聚焦时不抢占**。
   - 规则 B：`falsifyEvent`、`finalizeEvent`（若运行模式可触发）作用于当前聚焦事件后，聚焦对象改为分诊排序（见 T2 的 `sortTriage`）的第一名；若无活跃事件则置 null。
   - 规则 C：`voidPlan` 不改变聚焦。
4. `focusEvent` 实现：直接 `set({ focusedEventId: eventId })`；**同时**若该事件存在预案，调用 `setActivePlanVersion(该事件预案的最大 version)`，使预案面板立即切到该事件最新版本。
5. **测试**（追加到 `src/store.test.ts`，≥3 条）：
   - 运行模式下首个 ingest 事件自动获得聚焦；
   - 第二个 ingest 事件不抢占聚焦；
   - 证伪聚焦事件后，聚焦自动转移到剩余活跃事件（按 T2 排序第一名），无剩余则为 null。

### T2【engine】新增分诊排序纯函数

**新建文件**：`src/engine/triage.ts` + `src/engine/triage.test.ts`

1. 导出：
   ```ts
   export interface TriageInput {
     event: SimEvent;
     /** 该事件最新有效预案中 runState==='待确认' 的措施 shownAtMs 列表（无预案则空数组） */
     pendingShownAtMs: number[];
     simSec: number;
   }
   export interface TriageRow {
     eventId: string;
     escalated: boolean;      // 任一待确认控制类措施 confirmStatus==='escalated'
     overdue: boolean;        // 任一为 'overdue'（escalated 也算 overdue）
     pendingCount: number;
     queueKm: number;         // queueLength(event.w, max(0,(simSec-event.startSimSec)/60))，未拥堵为 0
     startSimSec: number;
   }
   export function buildTriageRows(inputs: TriageInput[], nowMs: number): TriageRow[];
   export function sortTriage(rows: TriageRow[]): TriageRow[];
   ```
2. `sortTriage` 排序键（**严格按此顺序，禁止自行发明**）：
   ① `escalated` 为 true 者在前 → ② `overdue` 为 true 者在前 → ③ `pendingCount` 降序 → ④ `queueKm` 降序 → ⑤ `startSimSec` 降序（新事件在前）→ ⑥ `eventId` 字典序（保证稳定）。
3. 复用 `engine/confirmTiming.ts` 的 `confirmStatus`（不复制阈值常量）与 `engine/flowModel.ts` 的 `queueLength`。
4. **测试 ≥4 条**：escalated 压过高 pendingCount；overdue 压过 queueKm；同参数时新事件在前；空输入返回空数组。
