## 五、重点代码审计发现

### P1：前端直连大模型 API Key 仅适合本地演示

位置：

- `demo/scripts/sync-llm-keys.mjs`
- `demo/src/services/llm.ts`
- `demo/src/components/RuntimeBar.tsx`

现状：

- `API KEY.txt` 会同步生成 `VITE_LLM_*_API_KEY` 到 `.env.local`。
- 前端通过 `fetch` 直接调用 OpenAI 兼容接口，并在请求头中携带 `Authorization: Bearer ...`。
- `.gitignore` 已覆盖 `API KEY.txt`，`.env.local` 也会被 `*.local` 规则忽略，不会默认进入版本库。

风险：

- 只要密钥进入 `VITE_*` 环境变量，浏览器运行时和打包产物中就可能暴露密钥。
- 本方案适合本地 MVP、封闭演示和离线评审，不适合作为生产架构。

建议：

- 生产环境改为后端代理调用大模型。
- 后端保存真实 Key，前端只拿业务会话令牌。
- 增加用户级限流、调用日志、脱敏审计和模型供应商失败降级。

### P2：GIS 地图雷视目标弹窗存在防御性加固空间

位置：

- `demo/src/components/GisNetworkMap.tsx:747`
- `demo/src/components/GisNetworkMap.tsx:768`

现状：

- 雷视目标弹窗使用 `node.innerHTML = ...` 拼接展示车辆属性。
- 当前车辆属性主要来自本地仿真数据，实际注入风险较低。

风险：

- 后续如果接入真实雷视、摄像机、设备或第三方接口数据，未转义字段进入 `innerHTML` 会带来 XSS 风险。

建议：

- 改为 DOM 节点 + `textContent` 组装弹窗内容。
- 或复用事件弹窗中已采用的安全 DOM 构造方式。

### P3：开发模式调试句柄需保持仅开发态

位置：

- `demo/src/components/GisNetworkMap.tsx:467`
- `demo/src/store.ts:800`

现状：

- 开发模式下暴露 `window.__map` 和 `window.__store` 便于现场诊断。
- 代码已使用 `import.meta.env.DEV` 限定。

建议：

- 保持该逻辑仅在开发模式生效。
- 后续发布前可增加一次生产包检查，确认调试句柄未进入业务可访问路径。

### P3：Kimi Key 配置状态需和界面提示保持一致

位置：

- `demo/scripts/sync-llm-keys.mjs`
- `demo/src/services/llm.ts`
- `demo/src/components/RuntimeBar.tsx`

现状：

- 系统已支持 Qwen、DeepSeek、Kimi 三种模型通道和模型版本选择。
- 本地密钥文件如缺少某个供应商 Key，对应供应商仍可被选择，但调用会提示未配置密钥。

建议：

- 在模型供应商下拉框中增加“已配置 / 未配置”状态提示。
- 当选择未配置 Key 的供应商时，提前给出明确提示，避免用户误以为模型不可用。

## 七、建议后续修复优先级

1. 将大模型调用迁移为后端代理，避免生产环境前端暴露 API Key。
2. 将 `GisNetworkMap.tsx` 中雷视目标弹窗改为安全 DOM 渲染。
3. 在系统配置弹窗中显示每个模型供应商的 Key 配置状态。
4. 为“图谱计算 + 大模型解释”增加端到端快照测试，验证切换不同模型供应商时界面状态一致。
5. 对地图页进行首屏性能优化评估，重点关注 `maplibre-gl` 分包加载时机。

## 八、最终判断

当前版本通过自动化测试和依赖安全审计，具备继续演示、联调和评审条件。需要注意的是，当前大模型 Key 的配置方式属于本地演示便利方案，若进入试点或生产环境，应优先改造为服务端托管密钥的安全调用架构。
