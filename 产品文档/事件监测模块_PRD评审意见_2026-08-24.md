# 事件监测模块 PRD · 评审意见

**评审对象**：`产品文档/事件监测模块_PRD_v0.1.md`（2026-08-24 首版）
**评审日期**：2026-08-24
**评审基线**：以 demo 目录当前代码 + README 为准（开发进度已超出《MVP 需求规格说明书 v1.0》）
**评审方法**：PRD 通读 + 与现有代码（store.ts / engine/ingest.ts / engine/merge.ts / engine/severity.ts / data/graphSchema.ts / services/persistence.ts / components/RuntimeBar.tsx 等）逐条交叉比对

---

## 一、评审结论摘要

### 总体评价

PRD 质量总体较高，具备较好的产品成熟度：

- **三层业务模型（Alarm→MonitoringEvent→ControlEvent）**划分清晰，准确界定了"监测"与"管控"的职责边界（监测负责发现/核实/分级/接管，管控负责研判/预案/执行/关闭）。
- **接管契约设计扎实**：幂等键（idempotencyKey）、接管快照、状态机（monitoring→pending_handoff→handoff_in_progress→taken_over/failed）、重试与失败人工队列，都体现了对"可靠移交"这一核心风险的正确认知。
- **边界意识强**：明确"监测等级≠法定事故等级"、"AI建议L4不自动接管"、"未经人工复核不直接创建L4管控事件"、"模拟数据标识不得隐藏"，与现有代码"控制类一律人工确认"的能力边界一脉相承。
- **架构意识正确**：建议新增独立 `src/monitoring` 领域而非继续堆入现有单一 store，符合现有"engine 纯函数 + store 编排"的分层约定。

### 必须解决的核心问题（评审结论）

1. **"八类交通事件"未定义清单**——这是模块的功能范围基础，当前无法据此开发与验收。
2. **L1-L4 建议等级缺判定规则表**——只有 L4 的列举和 L1/L2/L3 的抽象描述，无法实现与测试。
3. **去重/聚合评分规则未定义**——验收标准写了"聚合评分≥0.75"但无评分维度与硬规则。
4. **跨模块回写（管控→监测）数据契约缺失**——只有 HandoffRequest/Result，没有回写结构。
5. **FR 编号与章节不对齐，缺 4 个 FR 的详细规格**（002/003/011/013）。

以上 5 项均为 **[P0] 阻断级**，建议在 PRD 进入开发前补齐。其余问题见下文逐条清单。

## 二、与现有代码基线对齐的关键问题

### A1. [P0] "八类交通事件"未定义清单

**问题**：§8.1 提出"八类交通事件的告警、聚合、核实和闭环"，但全文未给出八类的具体清单。§7.2 仅列举了"行人、逆行、倒车、抛洒物及专业设施异常"五个缺口类型，加现有四类（追尾/侧翻/抛锚/危化品泄漏）也不足八类，且"专业设施异常"本身又是一组而非一类。

**与代码基线的冲突**：现有事理图谱 `data/graphSchema.ts` 只有 4 类事故类型节点（E_追尾/E_侧翻/E_抛锚/E_危化泄漏）；`components/RuntimeBar.tsx` 的事件上报下拉框同样只有这 4 类。新增事件类型将牵动：
- 图谱 schema（节点/边，graphSchema.ts）
- 五步推理触发逻辑（engine/reasoner.ts）
- 措施模板（data/measureTemplates.ts）
- 事件归并相容表（engine/merge.ts 的 COMPATIBLE_TYPES）
- GIS 图标/弹窗映射（gis/mapIcons.ts、gis/incidentPopup.ts）

**修改建议**：在 PRD 新增一节"事件类型体系"，定义八类交通事件的清单，并逐类标注：图谱节点归属、是否走现有专属推理、还是走 §21 的"通用安全研判"（无专属规则、需人工补充措施、不伪造专业结论）。这是后续一切设计（聚合、核实、等级、GIS、接管）的类型基础。

---

### A2. [P0] L1-L4 监测等级缺判定规则，且与现有 severity 体系关系未定义

**问题**：§19 只给出 L4 的列举（伤亡/危化品/隧道火灾/桥梁垮塌/重大滑坡/全幅封闭/关键节点失效）和 L1/L2/L3 的抽象描述（提示/一般/较重），没有可执行的判定规则表。同时 §5 声明"监测等级≠法定事故等级"，但未说明两套等级在系统中的关系。

**与代码基线的冲突**：现有 `engine/severity.ts` 已有 `assessSeverity`（特别重大/重大/较大/一般，含具体短路规则），并写入 `SimEvent.severity`（`domain/event.ts`）。PRD §19"建议复用 engine/severity.ts"的说法不成立——两套等级语义不同、维度不同，直接复用会造成概念混淆。

**修改建议**：
1. 补充 L1-L4 判定规则表：明确 §19 所列输入（类型/置信度/来源数/持续时间/车道/交通/敏感设施/人员/危化品/火灾/损毁）各自的权重或短路规则，与现有 severity.ts 的风格保持一致（规则短路 + 理由数组），便于实现与单测。
2. 定义 L3/L4 → 现有 `Severity`（特别重大/重大/较大/一般）的映射规则：接管后 ControlEvent 的 `severity` 字段如何赋值，需给出确定性映射（例如"L4→特别重大/重大、L3→重大/较大"，按具体触发原因细化）。
3. 明确 MonitoringEvent 的 `suggestedLevel/confirmedLevel` 与 SimEvent.severity 是两个独立字段，互不静默覆盖（PRD 已有"人工值不被后台静默覆盖"的精神，需落到字段层面）。

### A3. [P0] 去重/聚合评分规则未定义

**问题**：§23 定义了 Alarm/MonitoringEvent 数据结构，§29 验收 #1/#2 出现"重复发送10次只保留一个有效Alarm"、"聚合评分≥0.75只生成一个事件卡片"，但全文没有聚合评分规则。

**与代码基线的冲突**：现有 `engine/merge.ts` 已经实现了成熟的多维归并评分（空间 0.35/时间 0.25/类型 0.25/方向 0.15 + 关键字段冲突强制拆分 + 位置漂移阈值），PRD 的"去重/聚合"与现有"归并"在概念上接近但层次不同：
- **监测侧聚合**：把高频 Alarm 合成一个 MonitoringEvent（同一来源/摄像机短时间重复检测、多源同位置报警）
- **管控侧归并**：把标准化报告合成一个 SimEvent（现有 merge.ts）

**修改建议**：在 PRD 新增"告警去重与聚合规则"章节：
1. **精确去重**：定义"同一 sourceAlarmId 重复接收"的判定（验收 #1 的场景），以及重复计数保留策略。
2. **聚合评分**：定义维度（空间/时间/类型/来源）与权重、聚合阈值、以及硬规则（如关键字段矛盾强制拆分为两个 MonitoringEvent）。建议复用现有 merge.ts 的多维评分模式，明确"复用/扩展 merge.ts 还是新建 engine/alarmAggregation.ts"，避免将来与归并逻辑混淆。
3. **聚合的反向操作**：聚合后若两事件独立演化（位置漂移等），如何拆分（参考 merge.ts 的 groupDivergence 思路）。

### A4. [P0] 跨模块回写（管控→监测）数据契约缺失

**问题**：§22 只给了 HandoffRequest/HandoffResult（监测→管控方向），但 §21/FR-EM-010 要求的"智能管控回写"（管控事件ID、研判阶段、预案版本、待办数、下发状态、执行进展、解除、关闭、重新研判摘要）只有文字描述，无数据结构。FR-EM-010 还要求"版本冲突不覆盖、进入待同步队列并重试"。

**与代码基线的冲突**：现有 store.ts 有完整的状态机（plan.state：草案→待确认→已确认→已下发→执行中→已完成/已作废/已被替换）和审计流，但**没有向外部模块回写状态的通道**——需要新增跨模块同步层（PRD §31 也提到"跨模块关联状态"）。

**修改建议**：
1. 补充回写消息结构（如 `ControlEventUpdate`），明确：增量字段集合、版本号、correlationId（关联到 handoffId）、来源判定。
2. 定义状态映射表：`plan.state + 事件生命周期 → MonitoringLifecycle` 的确定性映射（例如"已完成 → monitoring 侧 resolved/closed"、"已被替换 → 重新研判摘要"）。
3. 明确权威字段归属：监测侧事实（核实的类型/位置/等级）以监测为准；处置状态（预案版本/待办/下发/执行）以管控为准；同名字段冲突时按归属仲裁（避免循环覆盖）。

### A5. [P0] FR 编号与章节不对齐，缺 4 个 FR 的详细规格

**问题**：§13 清单列了 FR-EM-001~013，但正文详细规格章节只覆盖了 001/004/005/006/007/008/009/010/012。缺失：
- **FR-EM-002 告警接收与标准化**（模块核心前置逻辑，只有 §10 流程图和 §23 数据结构）
- **FR-EM-003 去重、聚合与冲突处理**（同 A3，无详细规格）
- **FR-EM-011 持久化、断线与恢复**（仅 §26 部分覆盖）
- **FR-EM-013 算法效果与运营指标**（仅 §28 部分覆盖）

**修改建议**：为上述 4 个 FR 补齐与现有 FR 相同格式的规格条目（用户故事/主流程/业务规则/验收），或将清单调整与现有章节对齐（如将 011 并入 §26、013 并入 §28 并保留编号）。尤其 FR-EM-002 的"告警标准化"应明确：字段归一、非法值处理、时间戳口径（detectedAt/receivedAt）、模拟标识注入——这是数据进入系统的第一道门。

### A6. [P1] 持久化从 localStorage 迁移到 IndexedDB 论证不足

**问题**：§7.2 将"MVP 规格建议 IndexedDB、当前业务持久化主要为 localStorage"列为差距；§31 提出"IndexedDB和迁移"。但：
- 现有 `services/persistence.ts` 有明确注释说明为何用 localStorage（SPEC-DEVIATION：单机规模远小于 5MB、同步 API 让 store 无需异步化、显著降低复杂度），这是**有意的工程取舍**而非疏漏。
- PRD 未论证告警流（1000条/200活跃事件）是否真的超出 localStorage 容量（JSON 序列化后通常数百 KB，5MB 内完全可行）。
- PRD 未给出迁移方案：现有 RuntimeSnapshot version 3 如何升级？是否双轨兼容？迁移失败如何回退？

**修改建议**：
1. 补一段容量估算，论证迁移 IndexedDB 的必要性（如确实需要异步写入/更大容量/查询索引，才迁移；否则 MVP 阶段可维持 localStorage 并为监测数据划分独立 key 空间）。
2. 若决定迁移：明确封装选型（自封装薄层还是引入 idb 库——注意现有技术决策 D5"新增依赖上限，IndexedDB 封装可用 idb ≈3KB"）、版本迁移策略、以及"localStorage→IndexedDB"的回退路径（NFR-3 降级不静默失败）。

### A7. [P1] 模块导航与 UI 状态保持需求未落到架构

**问题**：§12 提出一级导航"事件监测/智能管控"，并规定"刷新恢复原模块和视图；切换保留筛选、选中事件、滚动位置和地图视角"。现有 `App.tsx` 是**单页四列工作台，无一级模块导航**，且现有 `store.ts` 只持久化业务快照（事件/预案/轨迹/环境/地图主题），**不持久化 UI 上下文状态**（筛选/滚动位置/选中项）。

**修改建议**：
1. 明确"UI 上下文状态"与"业务状态"的分层：筛选、滚动、选中、地图视角属 UI 状态，建议用 `sessionStorage` 或 store 内的独立 `uiState` 分区承载（刷新恢复），不得混入业务快照。
2. 明确一级导航与现有四列工作台的关系：监测模块（视频事件监测 + GIS 态势）是替代默认视图，还是与智能管控并列的二级视图？现有智能管控的五个案例/事件上报入口是否在监测模块下保留"应急直报"（§21 已提到）。
3. 建议给出 App.tsx 改造后的模块容器示意（一级 Tab → 模块视图 → 面板）。

---

### A8. [P1] 模拟告警适配器与现有案例/事件上报的关系未明确

**问题**：§24 提出统一 `MonitoringSourceAdapter`，页面只依赖适配器。但现有系统有两套事件来源：
- **五个案例**（`data/demoCases.ts`，loadDemoCase 会 clearRuntime 全量重置）
- **手工上报**（RuntimeBar 的"事件上报"直接 ingestEvent 进入智能管控）

PRD 未说明：模拟告警流与这两者的数据隔离、时钟同步、以及"应急直报绕过监测"（§21）的具体入口和标记方式。

**修改建议**：明确：
1. 模拟告警适配器的数据是否与现有案例数据隔离（避免加载案例时污染监测模块）。
2. 监测模块与智能管控的时钟关系（共用模拟时钟？监测告警流按真实时钟还是模拟时钟推进？）。
3. "应急直报"入口落在监测模块还是保留在智能管控顶部，以及"绕过监测"的标记字段（`sourceKind='manual_emergency'`?）如何进入现有 ingest 管道。

## 三、PRD 内部一致性与完备性问题

### B1. [P1] 核实时限与智能管控确认时效的衔接未说明

§18 定义监测核实时限（L4=1min/L3=3min/L2=5min/L1=10min）。现有智能管控有独立的"控制类措施确认目标 ≤3min"（FR-E2）。接管后是两套计时并存：监测核实倒计时 + 管控措施确认倒计时。PRD 应说明两者在界面和状态上的呈现关系（例如接管成功后监测核实计时停止，移交管控确认计时）。

### B2. [P1] 误报/降级复核规则需统一为矩阵

各处表述不完全一致：§17"L4误报须班长复核"、§19"L3/L4降级需依据；L4降级由班长复核"、§18"L4观察需班长批准"。**L3 误报是否需复核？L3 观察是否需批准？** 验收 #8 只覆盖 L4。建议补一张"等级 × 操作（误报/降级/持续观察）→ 是否需班长复核"的规则矩阵，消除歧义。

### B3. [P1] Alarm 模型缺算法版本字段，影响 FR-EM-013

§28（P1）要求"按算法版本统计人工确认率和误报率"，但 §23 的 Alarm 数据结构没有 `algorithmVersion`/`modelName` 字段。建议在 Alarm 补充算法版本字段（或在 sourceSystem 中约定编码），否则 P1 的算法效果统计无数据来源。

### B4. [P1] 证据与监控素材的 MVP 落地细节缺失

§17 规定"证据只保存 evidenceId、摘要和受控引用"，并对生产做合理约束（脱敏/人脸模糊/短期地址）。但 MVP 阶段视频证据来自何处未明确——现有 `components/MonitorPanel/MonitorDrawer` 使用演示 MP4/图片占位。建议补充：MVP 模拟证据的生成方式（模拟适配器产出什么素材）、"视频失败降级关键帧"如何在演示中触发。

### B5. [P1] 模拟用户权限的单机实现入口未定义

§6/§25 定义了四角色矩阵和跨区域主责/协同机构，MVP P0 含"模拟用户权限"。现有代码无用户概念（审计操作人记为"本机值班席"）。建议明确：模拟用户切换入口（顶部？）、默认角色、权限点清单、以及"管理员不能代替监控员作出业务结论"在 MVP 中如何演示（仅隐藏/禁用还是可越权拦截）。

### B6. [P2] "今日检测"等指标时间口径未定义

FR-EM-001 输出"今日检测、待核实、核实中、已确认、已误报、超时、已接管"。需定义"今日"的口径（自然日 00:00？滚动 24h？模拟时钟口径？），以及模拟数据下指标的基准（相对模拟时钟还是真实时钟）。

### B7. [P2] 术语中英对照与 UI 文案

项目开发约定"全部界面文案与代码注释使用中文"。PRD 大量使用 Alarm/MonitoringEvent/ControlEvent 英文术语。建议：数据结构字段名保留英文，但在术语表（§9）补充中文主名（告警/监测事件/管控事件），并约定 UI 文案统一中文（卡片显示"监测事件"而非 MonitoringEvent）。

### B8. [P2] "通用安全研判"的落地路径需细化

§21 提出未覆盖新类型进入"通用安全研判，明确需要人工补充措施，不得伪造专业结论"。这是很好的边界声明，但需明确：通用安全研判在现有引擎中落到哪条路径（是否复用五步推理的骨架、跳过专属措施匹配、输出占位措施并标记"需人工补充"），否则开发时无从实现。

## 四、非功能与验收标准问题

### C1. [P2] 性能验收缺测量方法与基准

§27 给出"新事件可见≤1s、筛选≤500ms、详情打开≤1s、GIS 1000点聚合、连续2小时无内存增长"等目标，但未定义：模拟数据的生成参数（告警速率、活跃事件数）、测量环境基准（机器配置/浏览器）、以及"无明显内存增长"的可量化判据（如 2 小时内存增长 ≤ X MB）。建议补充可复现的验收脚本口径（可与现有 Vitest + 浏览器冒烟结合）。

### C2. [P2] 高频告警的内存保留策略未定义

§27"连续2小时无崩溃和明显内存增长"与高频告警（1000条）、时间片历史（现有孪生讲解保留 12 条的做法）存在张力。建议定义：监测事件活跃上限（200 起）、关闭事件的归档/清理策略、Alarm 的保留条数上限，以及"大量重复告警更新聚合数量不重复发声"（§26）的实现约束。

### C3. [P2] 验收标准 #17 与 #5 的措辞建议

验收 #17"1000条告警和200起活跃事件组合筛选500ms内更新"建议注明是"本地模拟数据 + 开发机"前提，避免被误解为生产性能承诺。验收 #5"持续观察释放占用、设置复核时间并保留核实中主状态"与 #3"仅打开详情不进入核实中"建议在验收中补充"释放后事件可被他人重新占用"的断言，闭环核实占用语义。

## 六、建议的修改顺序

1. **先补范围**：A1 八类事件清单 + A5 补齐缺失 FR（002/003/011/013）。这两项决定模块边界，是其他所有设计的前置。
2. **再定规则**：A2 等级判定表 + A3 聚合规则 + B2 复核矩阵。这三项是核心业务算法，需形成可单测的确定性规则。
3. **然后定契约**：A4 回写契约 + A8 适配器/直报关系 + B3 算法版本字段。明确跨模块边界。
4. **最后补工程细节**：A6 持久化论证 + A7 导航分层 + B1/B4/B5 + 非功能（C1/C2）。

其中 A1-A5 共 5 项 P0 建议在 PRD 进入开发评审前完成；其余可在开发期同步细化。
